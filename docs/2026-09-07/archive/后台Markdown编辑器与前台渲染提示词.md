# 后台 Markdown 编辑与前台渲染：AI 实现提示词

请在现有项目中实现一套「后台 Markdown 编辑、前台 Markdown 渲染」的内容管理能力。

目标是让运营人员在后台用接近富文本的可视化 Markdown 编辑器编写内容，保存原始 Markdown；前台则将 Markdown 安全地渲染成排版清晰、适合阅读的文章/公告页面。

---

开始编码前，请先：

1. 阅读并分析当前项目的技术栈、目录结构、路由方案、UI 组件库、鉴权方式、数据库设计，以及是否已有文章、公告、知识库、文件上传或富文本相关模块。
2. 保持现有项目的框架、代码风格、组件规范和设计系统，不要为了实现本功能而重构无关模块。
3. 若已有内容管理、文章、公告或上传模块，优先在原有逻辑上扩展，而不是新建重复体系。
4. 先输出一份简短实施方案，明确将新增或修改哪些页面、接口、数据字段和组件，然后再开始实现。

## 二、整体功能目标

实现一套文章/公告内容管理能力，使一篇内容可以：

- 在后台创建、编辑、预览、保存；
- 在数据库中以原始 Markdown 字符串保存；
- 支持草稿和已发布两种状态；
- 已发布内容可在前台文章详情页访问；
- 草稿内容不能通过公开前台访问；
- 支持 Markdown 的常用排版能力、表格、图片、链接、列表、引用和任务清单；
- 前台能够安全、美观地渲染 Markdown。

注意：

- Markdown 原文必须是唯一真实数据源；
- 不要只保存渲染后的 HTML；
- 不需要实现代码块、语法高亮、代码复制、行内代码等任何代码展示功能；
- 编辑器工具栏中也不要出现代码块或代码相关按钮。

## 三、后台编辑器视觉与交互要求

### 1. 整体视觉效果

后台编辑页面应呈现一种简洁、现代、偏内容运营场景的编辑体验，整体效果接近常见知识库、文章后台或文档编辑器：

- 页面顶部有清晰的标题区域，例如“新建文章”或“编辑文章”；
- 标题输入框应突出、字号较大、无明显厚重边框；
- 标题下方可配置摘要、封面图、发布状态等基础信息；
- Markdown 编辑器主体是一个白色或浅色卡片区域；
- 编辑器顶部为横向工具栏，图标简洁、间距均匀；
- 工具栏底部使用细分割线与正文编辑区隔开；
- 编辑区域应足够宽敞，默认高度建议不低于 500px；
- 页面整体留白充足，不要做成密集的传统表单页面；
- 保存、发布等主要操作放在页面右上角或编辑器顶部右侧，视觉优先级明确；
- 使用项目现有的按钮、卡片、表单、提示消息和弹窗组件。

编辑器建议具有类似以下布局：

- 顶部：返回按钮 / 页面标题 / 保存状态提示 / 保存按钮 / 发布按钮；
- 中部基础信息区：标题、摘要、封面图、状态；
- 下方编辑器区：工具栏 + Markdown 编辑内容；
- 编辑器右上或工具栏右侧：可切换“编辑”“分屏预览”“仅预览”三种模式；
- 窄屏或移动端下，分屏预览自动改为上下布局，不能横向溢出。

### 2. 编辑器能力

使用与当前项目技术栈兼容、维护活跃的成熟 Markdown 编辑器库，不要从零实现 Markdown 解析器或复杂编辑器。

技术选型建议：

- React 项目优先评估 `@uiw/react-md-editor`、`md-editor-rt` 或同等成熟方案；
- Vue 项目优先评估 `md-editor-v3` 或同等成熟方案；
- 必须优先考虑与项目 UI 风格、TypeScript 和构建方式兼容的方案；
- 编辑器数据必须由 `contentMarkdown` 统一管理。

编辑器需要支持：

- Markdown 源码编辑；
- 实时预览；
- 编辑模式、分屏预览模式、仅预览模式切换；
- 编辑内容与预览内容实时同步；
- 合理的默认高度，支持拖动调整高度更佳；
- 编辑区域聚焦、滚动、光标定位体验正常；
- 不得出现代码块、行内代码、代码高亮、代码复制相关能力。

### 3. 工具栏功能

工具栏应使用简洁图标按钮，并为每个按钮提供 tooltip 或无障碍标签。

至少支持：

- 撤销；
- 重做；
- 加粗：`**文本**`；
- 斜体：`*文本*`；
- 下划线：
  - Markdown 原生不支持时，可使用受控 HTML：`<u>文本</u>`；
  - 前台渲染白名单必须允许 `u` 标签；
- 删除线：`~~文本~~`；
- 标题：H1、H2、H3；
- 无序列表；
- 有序列表；
- 任务列表：`- [ ] 待办事项`；
- 引用块：`> 内容`；
- 分割线：`---`；
- 表格；
- 链接；
- 图片插入与图片上传；
- 清除格式或格式辅助功能（若所选编辑器支持）。

交互要求：

- 用户选中文本后点击工具栏，应对选中文本应用对应 Markdown 格式；
- 未选中文本时，插入对应格式模板，并将光标放置到可继续输入的位置；
- 操作后不能丢失已有内容、选区或光标位置；
- 不要提供代码块、行内代码、代码语言选择、代码高亮等功能。

## 四、图片上传能力

如果项目已有文件上传能力，必须复用；如果没有，再按项目后端规范实现图片上传能力。

图片上传流程：

1. 用户通过工具栏选择图片，或将图片拖拽到编辑器内；
2. 前端校验图片类型和文件大小；
3. 上传至项目现有文件存储服务；
4. 上传成功后，自动在当前光标位置插入 Markdown 图片语法：

   `![图片说明](图片URL)`

5. 上传失败时必须展示明确错误提示，不能静默失败；
6. 上传过程中需显示 loading 状态，避免重复提交。

安全要求：

- 前后端都要校验图片 MIME 类型；
- 前后端都要限制文件大小；
- 后端必须校验上传权限和资源归属；
- 不允许上传脚本、可执行文件或危险文件；
- 不允许通过文件名、路径或上传参数覆盖服务器任意文件。

## 五、保存与发布体验

后台编辑页应具备可靠的内容保存体验：

- 编辑后显示“未保存”状态；
- 保存后显示“已保存”或最近保存时间；
- 保存按钮在保存中进入 loading 状态，防止重复点击；
- 保存成功与失败均需有明确提示；
- 保存失败时，编辑器中的内容不能丢失；
- 用户离开页面前，如果存在未保存修改，应弹出离开确认；
- 可以实现自动保存，但必须使用防抖，并保留明确的手动保存按钮；
- 发布前应检查标题和正文是否满足必填规则；
- 发布成功后记录发布时间；
- 支持撤回发布，撤回后文章不再公开展示。

## 六、数据模型与接口

请根据项目现有命名规范新增或扩展内容实体。至少应具备以下字段：

```ts
type ArticleStatus = 'draft' | 'published';

interface Article {
  id: string;
  title: string;
  slug?: string;
  summary?: string;
  contentMarkdown: string;
  coverImage?: string;
  status: ArticleStatus;
  publishedAt?: string | null;
  createdAt: string;
  updatedAt: string;
}
```

字段规则：

- `contentMarkdown` 保存原始 Markdown 正文；
- 标题不能为空；
- 正文不能为空，或遵循项目现有业务校验；
- 草稿默认不允许在公开前台访问；
- 发布时写入 `publishedAt`；
- 若项目有权限体系，只有具备内容管理权限的后台用户可以创建、编辑、删除、发布或撤回文章；
- 返回字段、提交字段、错误格式应完全遵循现有 API 风格。

接口可参考以下职责，但必须按项目当前 REST、RPC 或 GraphQL 规范调整：

- `GET /admin/articles`：后台文章列表；
- `POST /admin/articles`：新建草稿；
- `GET /admin/articles/:id`：获取后台编辑详情；
- `PUT/PATCH /admin/articles/:id`：保存文章；
- `POST /admin/articles/:id/publish`：发布；
- `POST /admin/articles/:id/unpublish`：撤回发布；
- `DELETE /admin/articles/:id`：删除；
- `GET /articles/:slugOrId`：前台已发布文章详情；
- `POST /uploads/images`：图片上传接口（仅当项目没有现有上传模块时）。

## 七、前台 Markdown 阅读页

实现公开文章详情页，例如：

`/articles/:slug`

页面应具备清晰、舒适、适合中文长文阅读的排版效果。

### 1. 页面结构

文章详情页从上到下建议包括：

1. 面包屑或返回入口（如项目已有此类导航）；
2. 大号加粗文章标题；
3. 发布时间、更新时间等文章元信息；
4. 摘要区域：
   - 使用浅灰、浅蓝或项目品牌色的低饱和背景卡片；
   - 与正文形成清晰区分；
   - 用于突出文章概览、说明或提示信息；
5. 封面图（如有）；
6. Markdown 正文；
7. 可选的上一篇/下一篇或相关推荐区域（仅在项目已有内容体系时实现）。

### 2. 正文排版

Markdown 正文应符合以下视觉要求：

- 正文阅读区域最大宽度建议为 760px 至 960px；
- 中文正文有舒适的字号、行高、段落间距；
- H1、H2、H3、H4 层级清晰；
- H2 应作为明显的章节标题，和上下正文留出足够间距；
- 无序列表、有序列表和任务列表缩进合理；
- 已完成任务应正确显示为勾选状态；
- 引用块有左侧强调线、浅色背景和适当内边距；
- 表格应具备边框、表头背景、单元格间距；
- 窄屏下表格允许横向滚动，不能挤压或破坏页面布局；
- 图片最大宽度不得超出正文容器；
- 图片应保持比例，可有轻微圆角或浅阴影；
- 链接颜色应清晰可辨，并有 hover/聚焦反馈；
- 分割线用于区分内容段落；
- 页面必须兼容桌面端和移动端；
- 不需要渲染代码块、行内代码、代码高亮或复制代码按钮。

### 3. 支持的 Markdown 语法

至少支持：

- 标题；
- 粗体；
- 斜体；
- 删除线；
- 下划线（受控 HTML 的 `<u>` 标签）；
- 引用；
- 无序列表；
- 有序列表；
- 任务列表；
- 链接；
- 图片；
- 表格；
- 分割线；
- GFM（GitHub Flavored Markdown）；
- 合理换行。

不需要支持：

- 代码块；
- 行内代码；
- 代码高亮；
- Mermaid 图表；
- HTML 中的复杂嵌入内容；
- iframe、视频嵌入或任意第三方脚本。

## 八、安全要求（必须落实）

Markdown 内容来自后台用户编辑，前台渲染时必须防止 XSS 和危险链接注入。

必须做到：

1. 使用成熟、安全的 Markdown 渲染方案：
   - React 优先使用 `react-markdown` + `remark-gfm` + `rehype-sanitize`；
   - Vue 可使用 `markdown-it` 配合 DOMPurify，或生态中同等安全的方案；
   - 必须结合当前项目实际技术栈选择。
2. 禁止直接将未经净化的 Markdown 转 HTML 后，通过 `dangerouslySetInnerHTML` 或 `v-html` 输出。
3. 如允许 HTML，仅允许严格白名单中的必要标签和属性，例如 `u`。
4. 必须禁止：
   - `<script>`；
   - 内联事件属性，如 `onclick`；
   - `javascript:` URL；
   - 不安全的 `data:` URL；
   - iframe；
   - SVG 脚本注入；
   - 任意危险 HTML 标签或属性。
5. 链接若使用 `target="_blank"`，必须带 `rel="noopener noreferrer"`。
6. 后端必须校验内容长度、用户权限、发布状态、上传文件类型和上传资源归属。

请确保：
