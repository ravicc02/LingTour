> 业务基线：[三类功能修改方案](feedback-modification-plan-2026-10-08.md)第 3 节。
> 流程规范：[AGENTS.md](../../AGENTS.md)；更新与验证结果写入 [CHANGELOG.md](../../CHANGELOG.md)。

## 1. 目标与范围

把路线发现、免费预约、收费定制和附加口译变成用户能理解的流程。视觉核心是“路线委托桌”：选择路线后，地图、行程和委托摘要随真实输入联动。

已确认业务边界：

- 固定路线可以真实免费预约，路线预约费用为 0。
- 免费请求不强制生成路线定金或进入支付。
- 定制路线收费，按需求、规划员分配、沟通、报价、用户确认和付款处理。
- 口译是独立收费服务，可单独请求或附加到路线；不能把口译价解释为定制规划总价。
- 第三方交通、住宿、餐饮和景点门票的包含范围必须说明。
- 保留现有认证、旧预约、口译套餐、历史订单与独立口译页。
- 本文只定义未来实现，不执行迁移、支付或生产写入。

定制报价、最低价、询价定金和履约容量尚未确认。界面应使用“待报价”，不填写虚构价格。现有美元套餐属于其他已进行的工作，本方案复用并核对，不重新定价。

## 4. 具体交互与视觉方案

### 4.1 第一层：两种路线选择

在 Route Planning 入口明确区分：

| 路线类型 | 初始信息 | 主要动作 | 提交后的状态 |
| --- | --- | --- | --- |
| Free Route | 已发布路线、城市、时长、预约费用 0 | 选择日期并免费预约 | Request received，待后台确认 |
| Specialized Route | 出行需求、服务范围与后续报价说明 | 填写定制需求 | Awaiting planner / quote |

视觉使用两个有实质差别的区域：固定路线为“已整理路线档案”；定制路线为“待填写委托页”。不采用两个外观相同、只换标题的价目卡。

桌面选择路线后，路线图、站点摘要和委托单联动。手机先显示路线信息和清楚按钮，进入表单后摘要可折叠。拖动或地图悬停只能增强体验，不能成为选择路线的唯一方式。

### 4.2 固定路线免费预约

完整流程：路线列表 → 路线详情 → Free Route Booking → 日期、人数、联系人 → 可选口译 → 检查摘要 → 免费提交 → 后台确认回执。

必须保留如下费用层级：

| 项目 | 呈现规则 |
| --- | --- |
| Route booking fee | 0，明确属于路线预约 |
| Interpretation | 未选时为不包含；选后显示服务端确认金额 |
| 门票、交通、食宿 | 明确包含或自理，不伪装为平台路线费 |
| Total due now | 无付款时为 0；附加服务需支付时单独解释 |

纯免费提交成功后显示持久回执和请求编号，不出现 PayPal 跳转，不停在 deposit_pending。附加口译付款取消时，免费路线请求的结果不能被抹除。

登录策略复用现有身份规则。若允许游客提交，联系方式只用于通知，不能以“相同邮箱”认领或读取私人请求。游客查看和后续对话必须经过验证码验证或安全登录认领。

### 4.3 定制路线收费委托

分组收集：城市、日期或日期范围、天数、人数、景点与饮食、住宿、预算、附加口译、补充需求、联系方式。

建议三步：Trip details → Requirements → Contact & review。只有确实需要的字段必填。预算允许“不确定”，但不把缺失预算自动解释为零。

桌面采用稳定的“需求编辑 + 委托摘要”；摘要实时反映用户输入。手机摘要折叠，底部动作条照顾安全区和虚拟键盘，不遮挡最后一项输入。

提交以后进入请求详情：待接收 → 已分配 → 沟通中 → 已报价 → 待确认 → 待付款 → 已付款/确认。取消与完成作为明确的终止分支。

报价页展示服务范围、总价、币种、付款或定金安排、有效期、取消条件和报价版本。用户先确认报价，再创建付款请求。报价修改后原确认不自动沿用。

### 4.4 交互记忆点与动效

| 场景 | 有意义的视觉机制 | 避免的问题 |
| --- | --- | --- |
| 选择固定路线 | 图上路线与档案摘要同步强调 | 只有图片放大，路线信息不变 |
| 切换定制模式 | 委托页替换路线页，说明字段与费用变化 | 静默保留失效套餐 |
| 完成某一步 | 摘要对应段落立即更新，焦点进入下一标题 | 整页跳动、自动滚屏和丢焦点 |
| 提交成功 | 显示真实请求编号与稳定回执 | 人为盖章动画代表实际未成功请求 |
| 收到新报价 | 差异高亮与版本说明 | 无提示覆盖旧报价 |

建议状态切换 150～250 ms，复杂过渡不超过约 350 ms。参数在原型中验证。减少动效时即时切换；付款与提交不能用乐观成功状态伪造完成。

## 5. 数据、接口和权限设计

### 5.1 请求模型

建议在现有预约基础上增量扩展，最终字段名由 DTO 与 migration 审查确定：

| 字段组 | 建议内容 | 约束 |
| --- | --- | --- |
| 归属 | ownerUserId、verifiedContact、serviceType | 服务端确定身份，服务类型为枚举 |
| 上下文 | citySlug、routeId、serviceDate、partySize | 检查路线发布状态、城市和关联一致性 |
| 定制需求 | tripDays、places、food、accommodation、budget、notes | 结构化收集，限长和校验 |
| 口译 | interpretationPackageId、requestedInterpreterId | 偏好不是成功指派 |
| 分配 | assignedPlannerId、assignedInterpreterId、assignmentHistory | 按角色与分配关系授权 |
| 快照 | routeSnapshot、requirementsSnapshot、pricingSnapshot | 历史记录不随 CMS 改动漂移 |
| 状态 | requestStatus、quoteStatus、paymentStatus | 分开存储，不用一个字符串承担全部状态 |

不要对旧数据猜测免费服务类型；旧 booking 保留为历史口译类型，逐条适配读取。新增必填项通过兼容方案和受控回填处理。

### 5.2 费用与报价

固定路线纯免费请求为 not_required。定制请求未报价时没有可支付金额，不应创建金额为 0 的假订单。

口译附加服务是独立费用项。若路线与口译共享一次支付，订单必须保存明细；若分开支付，回执要明确两笔义务。采用哪种模式须在接口实现前固定。

报价建议使用独立版本记录。付款创建时校验：请求所有权、当前有效报价、用户确认版本、币种、金额、定金规则与幂等键。客户端提交金额不作为计价依据。

重复提交、重复回调、付款取消、报价过期和退款都需单独定义。不得借本轮交互改造改写历史 SGD/CNY 订单金额或币种。

### 5.3 接口与后台

优先复用现有 booking 控制器和后台入口。是否新增统一 service-requests 模块，需要以兼容性和职责为依据决定，不能先建一套重复请求系统。

应提供的能力：免费提交、定制提交、本人请求列表与详情、规划员分配、文字对话、版本化报价、确认报价和付款创建。后台保留列表与详情抽屉，增加服务类型、处理状态、付款状态和负责人筛选。

会话必须绑定请求。用户、被分配工作人员和有审计权限的运营分别授权。分页、消息上传和读写端点逐一检查权限，不能只在前端隐藏按钮。

## 6. 影响范围、阶段与回退

| 阶段 | 改造内容 | 前置门槛 |
| --- | --- | --- |
| R1 | 固定业务、状态机、费用明细和游客认领规则 | 未确认报价规则不写成常量 |

迁移先增加兼容字段，生产前备份和检查迁移状态。回退时关闭新的服务入口并保留旧口译路径；不要撤销已支付义务，不删除新请求，不假设数据库 down 能恢复数据。

### 7.2 真实用户流程

在本地隔离数据中准备游客、用户 A、用户 B、规划员、无权工作人员和运营账号。优先复用本地已有路线，缺少数据时只创建明确标记的测试 fixtures，不写生产。

流程一：游客选固定路线 → 填日期人数 → 不选口译 → 免费提交 → 后台确认 → 用户查看回执。检查没有 payment/checkout 网络请求。

流程二：用户 A 提交定制 → 运营分配 → 规划员沟通并报价 → A 确认 → 沙箱付款 → 刷新和重登后状态仍一致。

流程三：A 选免费路线并加购口译 → 付款取消 → 免费请求仍可见 → 重新支付。用户 B、未分配工作人员不能读取 A 的请求与会话。

## 8. 结果视觉校验

### 8.1 视口与状态

使用 320、375、390、430、768、834、1280、1440、1920 CSS px，额外检查 1024 px 的布局切换。重点画面为：路线类型选择、固定路线摘要、定制需求、错误、提交中、成功回执、报价、付款取消和后台详情。

手机增加虚拟键盘打开、横屏、长城市名、长需求和底部安全区。桌面检查摘要与表单高度差；不能通过统一巨大空白伪装整齐。

### 8.2 视觉验收门槛

| 维度 | 通过标准 |
| --- | --- |
| 免费/收费 | 在进入表单前即可分辨；无需读长段落寻找价格含义 |
| 信息层级 | 当前步骤、摘要、费用和下一动作明确，只有一个主要提交动作 |
| 交互创新 | 路线、地图与摘要联动有业务价值；表单操作本身保持清楚 |
| 状态 | pending、error、success、awaiting_quote、awaiting_payment 均有可辨识画面 |
| 可访问性 | 错误关联字段，提交错误后焦点合理，Tab 和 Escape 行为完整 |
| 手机 | 无溢出、无键盘遮挡、无需 hover，触控目标至少 44 px |
| 视觉一致性 | 方正、浅色、克制材质；不将收费表单做成大面积暗色宣传板 |
| 减少动效 | 无移动也能理解类型、步骤和状态 |

截图须在固定字体、数据与视口下比较。人工检查“用户是否知道下一步会不会付款”，不能只做像素相似度判断。
