## 1. 目标与服务边界

公共日历是浏览城市活动的日期档案，私人 Calendar 是个人行程与记事工具。两者共享品牌和日期计算，分别处理数据、接口、授权和状态。

已确认要求：

- 首页默认今天，使用广东活动时区 Asia/Shanghai。
- 空日期可选，数据刷新不能覆盖用户日期。
- 公开活动按月完整查询，支持跨日、多条图片/视频、Event、Slogan 和补充信息。
- 回看历史日期时可查看当时展示的版本；普通编辑不覆盖历史快照。
- 在现有日历与后台活动结构上扩展，不新增商家名称必填字段和商家 CRM。
- Profile 新增 Calendar，原 Notes 仍是社区相关内容。
- 私人记事登录后持久保存，只有本人可读写；不公开到首页、社区和 Ticket。
- 首版不增加提醒推送、多人共享或日历外部同步。

## 4. 公共日历具体方案

### 4.1 静态结构与日期镜头

保持现有桌面左右栏、手机上下结构。左侧是月度日期索引，右侧是选中日期的活动档案。布局直接服务内容浏览，不恢复容易造成错位的左右 sticky。

建议视觉机制为“日期镜头”：选中日期后右侧图像、Event、Slogan、正文和关联入口同步变化。日期网格保持稳定，内容以短距离横移或裁切表达“查看另一日”。

- Today 使用文字按钮和明确标记；不能只有红点。
- 选中日期、今天、有内容、无内容、焦点五种状态区分，不能只靠颜色。
- 同一天多条内容显示可访问的列表或切换按钮，显示当前条目与总数。
- 活动密度通过有限标记或数量表达，不堆叠过多圆点。
- 空日显示选中日期、无内容说明，以及返回 Today 或查看本月活动的动作。
- 手机保留完整月历作为可靠入口；可加紧凑日期条，但不能强迫横向拖动寻找全部日期。

### 4.2 状态与日期语义

独立管理：todayKey、displayMonth、selectedDate、selectedEventId、monthData、requestState。月度翻页和日期选择不能由 events[0] 或请求完成顺序反向决定。

规则建议：

1. 首次进入使用服务端给出的业务 todayKey，避免 hydration 时区闪跳。
2. 客户端用同一时区计算跨日变化；未操作时更新今天，已操作时只更新 Today 标记，保留选择。
3. 翻月后加载新月数据。选中日期如何跟随采用明确规则：同日号有效则保留，否则落到该月末；不能偷偷跳到某活动。
4. Today 立即切回今天与当前月，取消已过时请求造成的回写。
5. 空日期始终可选，刷新后仍保留。
6. 日期采用 YYYY-MM-DD 纯日期值；不把本地午夜随意转换为 UTC 后截断。

翻月跟随规则属于本方案建议，原型测试后统一。浏览器前进/后退可使用本地状态或公开 query 参数恢复，不把私人笔记内容写入 URL。

### 4.3 月度完整查询

优先扩展现有 `/public/events` 的 startDate/endDate 契约。查询月度事件的区间条件：活动开始日不晚于月末，活动结束日（为空时取开始日）不早于月初。

接口需保证月度完整性：允许受限分页，但客户端必须知道 total/nextPage 并取全本月内容；不能把前 50 条当完整日历。返回必要的 date/endDate 和媒体字段，缓存键至少包含月份、城市与公开查询版本。

快速翻月采用请求取消或递增 request ID，旧请求不能覆盖新月份。已有数据保留显示并标记加载，失败允许重试；不能以无限 skeleton 代替错误。

### 4.4 活动媒体与详情

复用 title、summary、description、citySlug、date、endDate、relatedRouteSlugs。增量字段建议 media、slogan、extraInfo、displayOrder。

媒体项记录类型、URL、poster、alt、比例和顺序。旧 image 映射成单图兼容项。视频点击播放，切换活动或离开可见区域时暂停，音频不自动播放。

Know more 在当前日历内展开详情或已有风格面板。右侧展示活动本身，不再要求必须有关联路线。路线和城市链接作为次级动作，不新增独立商家页。

### 4.5 历史版本与可回看

采用轻量发布快照，例如 event_publications：eventId、version、displayFrom/displayTo、publishedAt、公开内容及媒体快照、排序、撤回记录。

“当日展示”需要区分活动举行日期、展示日期和发布时间：

- 活动日期描述活动何时举行。
- 展示日期描述内容在哪些日期进入日历展示。
- 发布时间描述运营何时发布该版本。
- 保存草稿只改草稿；发布新快照不能覆盖旧快照。
- 历史选择按约定解析展示版本；同一内容同一日期存在多个版本时必须有稳定规则，不重复列出所有内部编辑版本。

待明确的关键规则：是否允许新发布内容追溯改写过去日期。默认建议不追溯覆盖；历史勘误使用显式修订和审计记录。运营预览可查看版本列表，公众看到当日有效版本。

历史媒体必须保留引用和删除保护。上线前缺少的历史展示不能伪造；仅从首个真实快照开始承诺留痕。

### 4.6 后台编辑与发布

后台编辑器保留现有字段，增加媒体顺序、Slogan、展示日期、内容预览和版本历史。保存草稿、发布、停止未来展示、撤回历史内容是不同动作。

发布前预览使用实际公开渲染组件与数据契约。检查空标题、非法日期范围、视频无封面及资源不可用。权限、审计和媒体删除保护在 API 执行，不能只靠按钮确认。

## 5. Profile 私人 Calendar 方案

### 5.1 页面与交互

新增 `/profile?tab=calendar`，保留 Notes、Routes、Collection、Bookings、Settings。公共日历品牌材质可复用，私人 Calendar 采用更清楚的工作区密度。

桌面为月历、当日笔记列表、编辑面板；手机为月历、当日列表和可关闭编辑抽屉。同一天允许多条，空状态提供 Add note，不显示虚假的公共活动内容。

交互流程：选日期 → Add note → 标题与正文 → 保存 → 返回当日列表。编辑、删除使用明确操作。保存失败保留输入；删除失败保留原笔记。关闭未保存编辑器时提示处理草稿。

首版不默认使用 localStorage 存放私人正文。若需要离线草稿，需另定隐私、退出清理和共享设备规则。

### 5.2 数据与接口

建议新增 calendar_notes：id、userId、date、title、body、可选 citySlug、createdAt、updatedAt。userId 来自服务端会话；查询按用户与日期范围，增加归属和日期组合索引。

建议能力：本人月度笔记摘要、本人日期笔记列表、新增、编辑、删除。路由可归入现有 `/account/` 命名空间，最终命名由 API 模块设计确定。

每个读写请求按 userId + noteId 检查所有权。不允许请求体或 query 中的 userId 决定归属；非本人资源统一按项目策略返回 404 或拒绝访问。

并发编辑建议使用 updatedAt 或 version 检测冲突，避免不同标签页静默覆盖。校验正文长度、安全渲染和日期格式。后台不提供默认查看全部私人笔记的页面。

### 5.3 与公共事件的隔离

只共享纯日期工具、网格、焦点规则和品牌 token。public events 和 private notes 的请求、缓存、查询键与 loading/error 状态独立。

退出登录、切换账号、刷新认证后清理私人缓存，禁止把 A 的笔记留给 B。服务端缓存必须包含身份或禁用共享缓存；公共 API、Ticket 和社区不投影私人字段。

## 8. 结果视觉校验

### 8.1 画面、视口与动效

完整宽度为 320、375、390、430、768、834、1280、1440、1920 CSS px，并检查 1024 px 切换点。重点截图：今天有内容、今天空日、同日多条、跨日活动、视频封面、加载失败、历史版本、私人空日、新增/编辑及权限错误。

每个主要界面保存正常动效与 reduced-motion 终态。日期内容过渡建议为 180～280 ms、小范围移动或裁切；私人编辑只保留状态反馈，不做纸张飞入等舞台效果。

| 项目 | 必须达到的结果 |

## 9. 待确认与最终交付

需确认：历史版本的追溯修订规则、展示日期与活动日期关系、媒体保留周期、视频存储策略，以及私人笔记长度与并发冲突处理。默认不扩展提醒、共享和商家管理范围。

最终交付应包含：正确的月度公共日历、日期档案交互、多媒体、后台发布快照、历史回看、Profile 私人 CRUD、所有权保护、兼容 migration、真实浏览器测试、视觉证据和 CHANGELOG 结果。
